# Практическое занятие 3. Анализ запроса на изменение и план модификации

**Тема:** Анализ запроса - добавить настройку времени ожидания внешнего API
**Дата:** 10.11.2026
**Исходный запрос:** «Добавить настройку времени ожидания внешнего API»
**Текущее поведение:** Таймаут зашит в коде и равен 5 секундам. 

# Иструменты и условия
- OC: Windows 10/11
- IDE: Visual Studio 2022
- SDK: .NET 8
- ТЕстовый фреймворк: xUnit
- Логирование: Serilog / Microsoft.Extensions.Logging
- Выполнение локально

## 1. Проблема
Жестко зашитое значение таймаута (5 секунд) в коде HTTP-клиента делает приложение не гибким:
- при медленном API возникают ложные сбои(TimeoutException);
- при быстром API ресурсы удерживаются избыточно;
- невозможно адаптировать поведение под разные окружения без пересборки.

## 2. Ожидаемый результат

- Значение таймаута читается из конфигурации.
- При отсутствии параметра используется безопасное значение по умолчанию **5 секунд** (сохранение текущего поведения).
- Некорректные значения отклоняются на старте с понятным сообщением в логе.
- Изменение не ломает существующие сценарии запуска.

## 3. Допущения (подписаны явно)
- A1. Внешний API один; настраивается единый таймаут.
- A2. Конфигурация — переменные окружения + `appsettings.json`.
- A3. Приложение не использует пул клиентов с разными таймаутами.

## Шаг 2. Границы изменения (In Scope / Out of Scope)

## 4. Границы изменения

### В границах (In Scope)
1. Добавление параметра конфигурации `ExternalApi:TimeoutSeconds`.
2. Чтение параметра в HTTP-клиенте.
3. Валидация диапазона значений при старте.
4. Значение по умолчанию = 5 с.
5. Логирование применяемого значения при старте.
6. Unit- и integration-тесты.
7. Обновление `README.md` и примера `appsettings.json`.
8. Метрика `http_client_timeout_seconds`.

### Вне границ (Out of Scope) — сознательно не трогаем
- Изменение схемы БД.
- Изменение публичного формата HTTP-ответов.
- Настройка retry-политик (Polly).
- Таймауты для других внешних сервисов.
- Изменение контракта API (DTO).
- Рефакторинг других компонентов.

## 5. Критерии приемки

|№|Критерии премки|Способ проверки|
|---|---|---|
| AC-1 | При отсутствии параметра таймаут = 5 с | Unit-тест + smoke-запуск без переменной окружения |
| AC-2 | Значение из конфигурации применяется (напр., 10 с) | Integration-тест с подменой `IConfiguration` |
| AC-3 | Диапазон допустимых значений — от 1 до 60 с | Параметризованный тест (1, 30, 60 — ок; 0, 61, -5 — ошибка) |
| AC-4 | Некорректное значение (строка, 0, >60) — приложение не стартует, в логе — понятное сообщение | Integration-тест + проверка лога |
| AC-5 | Обратная совместимость: запуск без новой переменной работает идентично прежнему поведению | Smoke-тест, сравнение логов до/после |
| AC-6 | Применяемое значение таймаута выводится в лог при старте | Проверка логов при запуске |
| AC-7 | Метрика `http_client_timeout_seconds` экспортируется | Запрос к `/metrics` |

## 6. Затрагиваемые компоненты

| Компонент | Что меняется |
|---|---|
| Конфигурация (`appsettings.json`, env) | Добавлен раздел `ExternalApi:TimeoutSeconds` |
| Options-класс | `ExternalApiOptions` с валидацией |
| HTTP-клиент | `HttpClient.Timeout` устанавливается из Options |
| Валидация | `ValidateOptions` / ручная проверка в `Program.cs` |
| Тесты | unit, integration, configuration |
| Документация | `README.md`, пример конфига |
| Мониторинг | Метрика таймаута, INFO-лог при старте |

## 7. Формат конфигурации

```json
{
  «ExternalApi»: {
    «BaseUrl»: «https://api.example.com»,
    «TimeoutSeconds»: 5
  }
}
```

**Переопределение через переменную окружения:**
```bash
ExternalApi__TimeoutSeconds=10
```

**Диапазон:** `1 ≤ TimeoutSeconds ≤ 60` (целое число).  
**Реакция на некорректное значение:** приложение завершает старт с кодом != 0, в логе — `ConfigurationException` с указанием причины.

## 8. Анализ обратной совместимости

- **Поведение при отсутствии параметра:** `TimeoutSeconds` не задан → используется дефолт `5` (AC-1).
- **Старый запуск без переменной окружения:** работает идентично предыдущей версии (AC-5).
- **Публичный контракт API:** не меняется.
- **Схема БД:** не меняется.
- **Другие компоненты:** не затрагиваются.

**Вывод:** изменение **полностью обратно совместимо**.

## 9. План тестирования

### Unit-тесты
- `DefaultTimeout_WhenOptionMissing_IsFiveSeconds`
- `Timeout_FromConfig_IsApplied`
- `Timeout_OutOfRange_Throws` (параметризованный: 0, -1, 61, 100)
- `Timeout_NonInteger_Throws`

### Integration-тесты
- `Application_FailsFast_WhenTimeoutInvalid`
- `Application_Starts_WhenTimeoutMissing`
- `HttpClient_ActuallyUsesConfiguredTimeout`

### Configuration-тесты
- Связывание `appsettings.json` → `ExternalApiOptions`.
- Приоритет env-переменной над `appsettings.json`.

## 10. Эксплуатационное влияние

**Журналирование:**
- `INFO` при старте: `External API timeout set to {Timeout}s`.
- `ERROR` при `TaskCanceledException` / `TimeoutException` с указанием фактического таймаута.

**Метрика:**
- `http_client_timeout_seconds` (gauge) — текущее настроенное значение.
- Счётчик `http_client_timeouts_total` — количество срабатываний таймаута.

**Документация:**
- Обновлён `README.md`: описание `ExternalApi:TimeoutSeconds`, диапазон, дефолт.
- Добавлен пример `appsettings.example.json`.

## 11. План развертывания и отката

### Развертывание
1. Слить PR в `main` после прохождения CI.
2. Собрать артефакт, прогнать smoke-тест на staging.
3. Выкатить на prod через штатный pipeline.
4. Проверить в логах строку `External API timeout set to …`.
5. Убедиться, что метрика экспортируется.

### Условия отката
- Рост ошибок `TimeoutException` > baseline на 20% в течение 15 минут.
- Падение приложения на старте из-за невалидного значения в prod-конфиге.
- Аномалии в latency p95.

### Процедура отката
- **Конфигурационный откат** (предпочтительно): вернуть `TimeoutSeconds=5` или удалить переменную окружения → приложение вернётся к прежнему поведению без пересборки.
- **Бинарный откат** (если нужно): откатить образ/релиз к предыдущей версии через pipeline.

## 13. Вывод

**Что установлено:**
- Запрос заказчика переведён в конкретное изменение конфигурации HTTP-клиента с диапазоном 1–60 с и дефолтом 5 с.
- Изменение обратно совместимо: старое поведение сохраняется при отсутствии параметра.
- Некорректные значения блокируют старт — это исключает «тихие» ошибки в проде.
- Наблюдаемость (лог + метрика) позволяет контролировать применение настройки.

**На основании каких данных:**
- Текущий код содержит константу `Timeout = 5s` (точка изменения).
- Требования к диапазону (1–60) — типовые для HTTP-клиентов; обоснованы практикой.

**Какие ограничения остались:**
- Не рассматривались retry-политики и circuit breaker — это отдельное изменение.
- Не рассматривалась индивидуальная настройка таймаутов на разные эндпоинты.
- Не проводилось нагрузочное тестирование — требуется отдельным этапом.
